## 1 每门重点课自己的活体元件（`school_courses.LIVE` + `_live`）

一套机制、十五份规格（而不是十五个手写动画）：`kind + label + period`，五种 kind 覆盖"机器在执行"的不同说法：

| kind | 画什么 | 用在哪几门 |
|---|---|---|
| `pulse` | 轨道上一个跑动的点 + 尾迹 | 嵌入式（5V 总线）、软件工程（数据流）、计网（seq） |
| `count` | 停不下来的数值 + 进度条 | C（addr）、机操（%CPU）、计组（A/Q）、软件测试（cov %） |
| `sweep` | 往复填充的条 | 算法设计（T(n)）、软件项目管理（sprint 3）、深度学习（loss） |
| `blink` | 按自己的周期亮灭的指示灯 | 大型工业软件（solver）、工业模型（mesh） |
| `cursor` | 走动的光标 + 十六进制串 | 数据结构（search 8）、面向对象（dispatch）、数据库（scan） |

**这些行是预留的，不是在图里找空位**：`draw_course` 把绘图框缩两行，机件带占最后一行、活体元件占倒数第二行。
第一版把元件画在 `by0 + row`（图内部），结果把课程自己的标注覆盖了——`cases` 变成 `c 4es`、`defects` 变成
`defec▓s`。**`pane_probe` 当时是 0 问题**（都在 pane 内），只有逐行 dump 看得出来。

顺带修掉 `c_test` 自己的老毛病：坐标轴标注原来和矩阵行号、直方图条同处一行，`cases`/`defects` 被压掉。
现在标注各占一行，直方图条从标注右侧起画。

## 3 两处**真实的性能回归**（本批最重要的发现）

做帧时间实测时发现的：在 197×52、全层开启下，**冷帧平均 1039 ms、最坏 5098 ms**（预算 41.7 ms/帧）。

| 位置 | 原因 | 修法 | 结果 |
|---|---|---|---|
| `school_fx._paper` | 批次 11 把去背景从"去白纸"改成"量边框色 + 泛洪"，于是**飞机/魔鬼鱼的黑底照片真的被泛洪了**：1536×1024 = 150 万像素，Python 逐格 BFS | **先缩放再去背景**（缩到目标格子尺寸的 2 倍后再泛洪，约 3 万像素） | 每条 2–5 s → **40–70 ms**；去白纸时旧代码只访问边界一圈，所以这个坑一直藏着 |
| `school_sculpture.source` | 同一类：扫描图（何尊等）在**全分辨率**上去纸 | 先缩到长边 ≤ 420 再泛洪 | 何尊 1899 → **24 ms**，剑 605 → 22 ms，memory 1145 → 154 ms；五个合计 3786 → **412 ms** |
| — | 首次解码仍会落在某一帧里 | 新增 `school_fx.warm()`，在**第一帧**把全部 sprite 预解码（打印 `warm: N sprites ready`） | 冷帧平均 305 → **55 ms** |

修后实测（同一组 21 个时间点）：

```
cold: mean   55.0 ms   worst  160.3 ms at t=200.0
warm: mean   19.7 ms   worst   33.2 ms at t=163.0
budget 41.7 ms
```

热帧（持续播放时的常态）平均 19.7 ms、最坏 33.2 ms，**在预算内**；冷帧只剩一次性预热成本。

这类缺陷值得单独记一条：**它不会让任何机检变红**——`pane_probe`、`span_probe`、`trans_probe`、两条 sweep
全绿，因为它们量的都是"画得对不对"，不是"画得多久"。发现它的唯一办法是**按帧计时**。
