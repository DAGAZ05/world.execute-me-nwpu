## 1 「相当多的字符显示混乱」——三个真的宽度 bug，都在渲染器里

这一条是整批里最实的一条，而且**所有 `_dev` 探针都看不见**：它们读的是 `Screen.buf`，也就是播放器
*打算*画的东西；用户看的是 `render_diff` *写出去*的东西。所以先写了一个新探针 **`_dev/ansi_probe.py`**：
把播放器自己吐出的 ANSI 逐帧解码回一块屏幕（光标定位、SGR 真彩色、宽字符占两列），再和缓冲区逐格
对比，全曲逐帧跑。第一次结果：**425 个抽样帧里 341 帧不一致**；逐帧跑是 **5084 帧里 561 帧**。
三个原因，都是宽度：

### 1.1 光标列 ≠ 单元格下标（这是主因）

```python
out.write(f"\x1b[{y+1};{x - len(run) + 1}H" ...)      # 错
```

一行里，**列和格是两把尺子**：一个 CJK 字符是 *一格两列*，它后面的占位格是 *一格零列*。原来的写法
假设每格一列，于是**同一行里每出现一个汉字，后面所有内容的列坐标就往前偏一格**。这部片子的页眉、
页脚、会话框全是中文——所以大部分行都被写偏了，字形互相压在一起。修法是让循环同时维护终端的列
（`col`），run 的起始列 = `col - _text_w(run)`（`_text_w` 把宽字符算 2 列、占位格算 0 列）。

### 1.2 占位格不是格子，而它坏了就永远不会被修

`put` 在宽字符后面写一个"占位格"（字符是空串，`wide=True`），`render_diff` 一律跳过它——这是对的，
但也意味着**一旦有别的东西写进那一列**（一个空格、一条边框、面板的边缘），字形就只剩右半被擦掉，
而它自己再也不会变化，于是 `render_diff` 永远不会重画它，**这个破损会留到那个字符消失为止**。
现在 `render_diff` 遇到"变化的占位格"会把它的**字符**重新写一遍（两个字列一起修好）。

### 1.3 谁都能把一对拆开：写者必须成对

`_dev/_invariant_trace.py`（一次性诊断）把 2 格不变的两种情况都抓了出来，涉及这些写者：`put`/`fill`
（写入前先把相邻的半格"除名"）、切开时的揭示（占位格不能先于它的字符到达）、**面板转场 `_carry`**
（原来把宽字符当一格搬——每一次切口都会拆开一批字，这就是"相当多"的来源）、闪烁字形 `_fx_front`、
抖动时的整行旋转、以及碎片飞散。它们现在都走 `Screen.set_cell`／`fill`，一条规则只写在一处。

**最后一道保险**：`Screen.normalise()` 在 `fx_apply` 之后把整帧的两格关系校一遍——因为渲染器是拿
缓冲区和**它自己的上一帧**比较的，一次"修好之后恰好等于上一帧"的修复不会被写出去，只有这一遍知道
要强制写。它只扫**有宽字符的行**（`put`/`set_cell` 记 `cjk` 行标记），所以代价与屏幕上的中文量成正比，
不是与屏幕大小成正比。

结果（`_dev/ansi_probe.py`，全曲逐帧 5084 帧）：**修前 561 帧不一致 → 修后 0**（见
`字符对照_修前.txt`；终局日志见 `check_full.txt` 同目录的 `终端对照_全曲0.txt`）。附带修掉一个同类的：
页眉右侧的章节名用 `len()` 对齐（中文两个字要占 4 列），最后一个字因此落在最后一列上、没有位置放
占位格 → 终端把它折到下一行。代价：`render_diff` 每格多一次"这一格可能是宽字符对"的检查，`draw` 末尾
多一遍只扫中文行的 `normalise()`——197×52 热帧最差 24.3 ms（批次 26）→ **34.7 ms**，仍在 41.7 ms 预算内。

## 2 像素画视觉：查了资料，落了一条

搜到的做法里，与这部片子直接相关、且能在这套代码里低风险落地的有三类：**抖动（ordered dithering）**、
**子格字符**（quadrant 2×2 / braille 2×4 / sextant 2×3，等于用同一个格换 4~8 倍分辨率）、
以及**轮廓/发光**（`chafa --symbols`、`libcaca` 的 dither，`textual-hires-canvas` 的 braille 思路）。
参考：<https://pypi.org/project/textual-hires-canvas/>、<https://vectree.io/pdf/c/libcaca>、
<https://skills.rest/skill/pixel-art-studio>（palette discipline + dithering + 质量打分）。

这一批落地的是**有序抖动**（另加批次 26 的白框，属于第三类）：五级灰度把照片的天空和阴影压成五条
硬边，这就是"单调"的来源；现在每个格子按 4×4 Bayer 矩阵在量化前偏半级，两级之间的边界变成棋盘格。
`DITHER = 0.5`，`BAYER4` 常量在 `school_fx`。子格字符留作下一批：它要重写 `sprite` 的字符映射
（`▀`+前后景色 → quadrant 四分之一块），是好事但会动到每一张图，值得单独一批做。

## 4 简化：心形曲线只画一个大的

`MOTIF_IN["pane_love_class"] = "epicycles"` + `MOTIF_ALSO["pane_love_class"] = "hearts9"`：LOVE 面板
下面是**两张母题带**，其中 `hearts9` 是 3×3 的九颗小心形加九条方程。用户的例子就是它。现在：
类清单只留四行（"the algebraic expression of love" 就是那几行），下面整块交给**一颗大心形**
（`r = 1 − sin θ`，两条等高线，随节拍呼吸），两条母题带都撤掉。顺带修了一个几何错误：心形是从
**尖点向下**长的（`r=1−sinθ` 在上端为 0、下端为 2），原来把 `cy` 当中心，于是每一个框里心形的尖
都被切掉。

## 6 运-20：屏幕中间至少覆盖 2/3

原来 `size = cols * peak`，给的是**贴图**的宽度；可这张照片四周是天空，飞机本体只占贴图的
**100% 宽 × 54% 高**（`_ink_share` 量的）。所以"贴图占 2/3 宽"= 屏幕上一个横条。现在按**覆盖率反解
尺寸**：让飞机本体的面积 ≥ 2/3 屏面积，

```
want = sqrt(cover · cols · rows · CELL_ASPECT · aspect / (share_w · share_h))
```

197×52 下解出 **198 格**（屏宽 197）——机翼顶到两边、机身 34 行高，也就是用户要的 2/3
（出图 `t0012_15_运20覆盖三分之二.png`）。同时按**本体**而不是贴图框定位，所以中间那一刻机身正在
屏幕中间，而不是被天空顶偏。

## 8 运-20 再放大一档（允许超出屏幕）

用户第二次提这件事："运20视觉冲击还是不够，让其更大，允许超出屏幕"。上一条按**覆盖率**解出 198 格
（屏宽 197）——本体确实覆盖 2/3，但视觉上还是"一条弧线"，因为侧视飞机的**高度**才是不够的那一维。
现在两者取大：`size = max(want, cols * peak) * frac`，`peak = 1.45`（与校门走进校门同一个数），
197×52 下是 **285 格贴图、90 行高、机身约 49 行**——比屏幕宽 45%、机身比屏幕中段还高，左右被裁掉，
正是"从下面掠过"而不是"看一张飞机的照片"。

**顺带必须做的性能修复**：285×90 的贴图在屏上约一万格，而 `paste` 是逐格 `Screen.put`（每字符一次方法
调用 + `CLEAR` 查询 + 两格校正）——实测那一帧 **60.4 ms**，超出 41.7 ms 预算一半，而且正是全片最有冲击力
的那一秒。现在 `paste(..., fast=True)` 直接写 `buf`/`wide` 并把暗角内联（`CLEAR` 检查对"这一层正要覆盖
的格子"本来就是多余的），**60.4 → 18.9 ms**；只有整屏贴图走这条路。
