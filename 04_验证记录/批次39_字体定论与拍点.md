## 1 子格字符族：**本机字体下不可用**（一条负面定论）

批次 27 把 `quadrant / braille / sextant` 留作"值得单独一批做"，批次 35 的审计也把它列为
"分辨率再翻一倍"的最大机会。**本批去量，结论是否定的。**

### 1.1 探针本身先崩了

`_dev/glyph_probe.py` 在写下的那天起**从未在这个 checkout 跑过**（`_dev/out/glyphs.png` 不存在
就是证据）。第一次运行直接崩溃：

```
UnicodeEncodeError: 'gbk' codec can't encode character '\u2580' in position 59
```

它把**字形本身**打到 stdout，而 Windows 控制台是 GBK——**探针在它唯一要测的那个字符族上崩了**。
另外两处让它无法给出可信结论的问题（批次 35 审计已指出）：

- `FONTS` **漏了 `consolab.ttf`**，而那是播放器自己为等宽输出指定的字体（`tui_live._F_MONO_B`）；
  `consola.ttf` 是**渲染器**的 ASCII 字体（`tui_shot`）。也就是说探针测的字体和片子画图用的字体不是同一个。
- 加载失败返回 `-1`，而空字数只统计 `0`——**一个完全加载不了的字体被报成"0 blank of N"，即满分**。

三处都修了：输出改为纯 ASCII（字形只进 PNG）、`consolab.ttf` 提到列表首位、`-1` 计为
`FAILED to measure`。并新增一行的最终判定。

### 1.2 修好后的一行答案

```
quadrants  usable in: NONE
braille    usable in: NONE
sextants   usable in: NONE
```

六种字体（`consolab.ttf` / `consola.ttf` / `msyh.ttc` / `msyhbd.ttc` / `simsun.ttc` / `SimHei.ttf`）
**全部**把这三族渲染成**同一个 `.notdef` 方框**：

| 族 | `consola` | `msyh` | `simsun` |
|---|---|---|---|
| blocks | ok (45–221 px) | ok (22–190) | partial: 14 blank of 32 |
| quadrants | SAME INK for all (53 px) | SAME INK for all (68 px) | NO GLYPH (all blank) |
| braille | SAME INK for all (53 px) | SAME INK for all (68 px) | NO GLYPH (all blank) |
| sextants | SAME INK for all (53 px) | SAME INK for all (68 px) | NO GLYPH (all blank) |
| shade | ok | ok | partial: 2 blank of 3 |

现代字体（`consolab`/`consola`/`msyh`/`SimHei`）给出的是**同样的墨量**——即同一个方框；
`simsun` 干脆是空的。**没有一种可用。**

### 1.3 这条定论的意义

**它反证了批次 35 的判断是对的。** 那一批没有去碰子格字符，而是把**已有的**半块路线做成真双色
（`▀` 前景 = 上半色、背景 = 下半色）——**不依赖任何新字形就把每格信息量翻倍**，
实测 `mascot` 65×44 的 1641 格里 1552 格带上了下半格颜色，航小天全身、校徽、两只手、图书馆
的效果改善是决定性的。

如果当时先做子格字符，会在**每一台机器上**得到一片方框。

> 同时留下一条对未来有用的判据：**这幅画能到什么分辨率，取决于运行它的终端字体**，
> 而 `glyph_probe.py` 现在能一行回答。换机器（或换字体链）之后应当重跑一次——
> 但**不要**把子格字符写进画法里，除非那一刻的答案不是 `NONE`。

## 2 `pane_isolation`：注释说的和代码做的不是一件事

`school_scenes.pane_isolation` 的注释写着：

> the field: nine points a row, **each one going out on its own beat**

而代码是：

```python
beat = 0.62 + 0.38 * abs(math.sin(t * 2.1))
```

`sin(t * 2.1)` 的周期是 `2π/2.1 = 2.99 s`，而歌曲的拍是 `0.4615 s`——**两者约每七拍才同相一次，
其余时间一路漂移**。它读起来是"有东西在呼吸"，从来不是"这台机器还在数"。

改成电影自己的拍点时钟 `FP.pulse(t)`（拍上为 1、140 ms 内衰减）——也就是
`tui_live` 让每个框呼吸、以及批次 38 让 `EXEC` 计数器回答的那同一个时钟。

顺带把"场正在朝中间排空"这件事画出来：**即将消失的点比还有时间的点更暗**
（`far > int(u*60)+24` 判据），所以那一段从"闪烁"变成"由外向内熄灭"，而这正是这一屏要说的事。

实测（`beat = 0.55 + 0.45 * pulse`）：

| | pulse | 幸存点前景 |
|---|---|---|
| 拍上 | 1.000 | **(255, 204, 0)** |
| 拍间 | 0.117 | (155, 125, 5) |

确定性保持（同一 `t` 两次绘制逐格相同）。

> `_beat()` 是本批新增的模块级小工具：惰性导入 `film_panels` 并加保护——这个模块也会被不导入
> 电影时钟的探针加载，此时退回到"与拍同频的正弦"而不是常数，因为常数会让
> `_dev/clock_probe.py` 把这一屏判成静帧。

## 4 本批**没有**做的，以及为什么

### 4.1 "61 行无事件 / 26 个空窗"——**不按审计的建议加整屏事件**

特效审计把"79 行日程里 61 行无整屏事件、26 个空窗 ≥2 s、最长 `pane_curriculum` 10.62 s"
列为最大的缺口，并建议在这些窗口里补 `lowpass` 级的整屏演出。**我不采纳整屏那一半**，理由是实测的：

- **`pane_curriculum` 那 10.62 s 不是死画面**：它按自己的时钟走（亮起的年份栏每 1.4 s 前进一次，
  `row_probe.LONG_OK` 里有具名理由），而那一段左窗同时在出「大一。先记住这三门。」等三块对话；
- **`clock_probe` 是 0 still**：78 行里没有任何一屏在揭示完成后静止而无理由——也就是说
  "空窗"指的是**没有整屏事件**，不是**没有动的东西**。这两件事被审计混为一件了；
- 而**在空窗里加整屏事件有已知的代价**：整屏层画在页脚与会话窗之上且不重画，
  这正是"篮球面板被埋"和"caption 压进度条"两个用户报过的缺陷的来源。往 61 行里各塞一发，
  正是把已经修过两次的那类缺陷重新引入。

**采纳的是那批建议里"低级但有效"的另一半**——逐格写入光标、扫描高光、薄噪声，
它们只在 pane 内部画、不进整屏层、不碰 chrome，代价 0.1–0.5 ms/帧。
本批先做了 `pane_isolation`（它同时是**名实不符**，所以优先级最高）；
`pane_curriculum` 的扫描高光是同一类改动，留下一批。
