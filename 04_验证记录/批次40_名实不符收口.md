每条都先用计算或渲染读回判定，再改。

## 1 `c_ds_algo`：三栏布局**从写下那天起就没生效过**（本批最重的一处）

### 1.1 怎么发现的

本批为了核实"搜索 8"那条，我把 `pane_exec_ds` 整屏 dump 出来（95×30）。看到的是：

```
y04 | ── 红黑树 · 插入 ─────────────── (满宽)
y06 |              ◎10
y09 |        ●5              ●15
y12 |    ●3      ●7      ●12     ●18
y14 | 插入 15/15 · 黑高相等
y15 | ── 复杂度 ──────────────────── (满宽)
y22 | ── 对照 ────────────────────── (满宽)
```

**三张图是竖着堆的，不是并排**；中间有一片空行；而树只画了 **7 个节点**（深度 0–2），
却在同一屏写着 `插入 15/15`。

### 1.2 根因：一个静默的尺寸守卫

`c_ds_algo` 的意图是并排三栏，docstring 明写理由（"Stacked, each one is thirty cells of content in a
hundred and thirty cell row and the pane reads as three quarters empty"）。条件是：

```python
cols = k.columns(3, [10, 7, 9], mins=[40, 26, 30])
if len(cols) == 3: ...   # 并排
# 否则落到堆叠分支
```

而 `_Kit.columns` 拒绝的条件是 `sum(need) + 2 * (n - 1) > bw`，即 `40 + 26 + 30 + 4 = 100` 列。
**这个 pane 在 197×52 下的体宽是 95。** 所以判断永远为假，**并排分支一次都没执行过**——
每一帧都走了它自己论证过不该走的堆叠分支，树拿到 11 行而不是 28 行。

这正是审计 N-7 那条（"`columns()` 要 `bw≥100` 而 pane 体只有 95"）**从批次 31 起一直没修**的那一项，
它当时被记为"版面取舍"。dump 证明它不是取舍，是**没生效的代码**。

### 1.3 修法：下限取"各图自己守卫的值"，不是"它想要的宽度"

三张图内部各自有守卫，宽度下限应当**读自那些守卫**：

| 图 | 内部守卫 | 需要 |
|---|---|---|
| `_ds_tree` | `depth = 3 if k.bw >= 34 else 2` | ≥34 才有深度 3（15 个节点） |
| `_ds_curves` | 画三条曲线 | 22 |
| `_ds_table` | `if k.bw < c1 + 2*c2: return`，`c1=12, c2=9` | **≥30** |

改成 `mins=[34, 22, 30]`（合计 90 ≤ 95），三栏并排生效。

### 1.4 我自己在这里犯了一个错，被 dump 抓住

第一版我把第三个下限写成 **26**——于是 `_ds_table` 的 `bw < 30` 守卫直接 `return`，
**第三栏整栏空白**。frame dump 一眼看出（那一列只有分隔线没有内容）。

这不是"窄一点"，是**没有这一栏**。改成 30 之后三栏都有内容：

```
y04 | ── 红黑树·插入 ────── │ ── 复杂度 ────── │ ── 对照 ────────────
y06 |        ◎10           │                  │ 结构      平均     最坏
y21 |  ●1 ●4 ●6 ●8 ●11 ●13 ●17 ●20  │  │· ······      │
y26 |  ① 根与叶为黑         │ 横轴 = 元素个数 n  │ 二叉树最坏退化成链。
```

**树现在长到深度 3、15 个节点全部出现**，`插入 15/15` 才名副其实。

## 2 `_ds_tree` 的"搜索 8"停在 7（真缺陷）

`lit = set((0, 1, 4)[: 1 + int(u * 2.99)])` —— 点亮键 **10 → 5 → 7**，而这一屏的标题就是搜索 8。

在这棵树（键表 `[10,5,15,3,7,12,18,1,4,6,8,11,13,17,20]`）上重放一次查找：

```
a search for 8 walks indices [0, 1, 4, 10] -> keys [10, 5, 7, 8]
```

**真实路径是四个节点**，代码停在第三个。改成 `path = (0, 1, 4, 10)`，并把揭示分成四段
（`int(u * 3.99)`），让"抵达"发生在最后。

> 这条也解释了为什么第 1 节那个缺陷一直没被察觉：**树只画到深度 2 的时候，键 8 根本不在屏上**，
> 所以"点亮它"本来也无从谈起。两处缺陷是叠在一起的。

## 3 排除一条审计误报：红黑树着色**没有**违反不变量

审计说 `(i + 1).bit_length() % 2 == 0` 在 depth=3 时把叶节点涂红，而屏上印着「① 根与叶为黑」，
两者矛盾。

我按标准定义逐条验（`_dev` 临时探针）：

```
invariant 1 (root is black):                root black? True
invariant 2 (a red node's children are black): nodes with a red child: none
invariant 3 (equal black height):          black heights = [2] -> equal? True
```

**三条全部成立。** 原因是**审计把"叶"理解成了画出来的最底行**——而红黑树的叶是 **NIL 外部节点**
（空指针），它们本来就是黑的、本来就不画。depth=3 的那些红色节点，它们的两个子节点是 NIL，合法。

**代码是对的，不改。** 这已经是本项目第三次遇到"审计的量法/读法有偏差"（前两次：宽高比把图例文字
量了进去、`err:` 重复行来自文档分桶渲染）。

## 4 `g_pareto`：图例承诺了一条**从未画出的**累计线

屏上一直印着 `cum 80% ──`（带一个线形字符的图例），而**整帧的 amber 格计数是 0**：
让帕累托图成为帕累托图的那条曲线不在，标签指着空气。

数字本来就在代码里：缺陷数 `42, 27, 15, 9, 5, 2` 合计 100，累计即 **42 / 69 / 84 / 93 / 98 / 100 %**，
**在第 3 根柱上越过 80%**——而那正是这台仪表存在的意义（"这三类缺陷占了五分之四"）。

现在真画出来：每根柱一个 amber 圆点、柱间虚线相连、随 `u` 逐段揭示。
（这一处同时修了我的探针 bug：我第一版用**精确相等**匹配 `(255,204,0)`，而 `_mix(AMBER, 0.95)`
是 `(242,193,0)`，于是把已画出的曲线报成 0。改成容差比较后 22 格、跨 5 行。）

## 5 `g_fem`：标着 `mesh`，而竖线**一个都没有**

渲染读回的字符普查：

| | 修复前 | 修复后 |
|---|---|---|
| `─` 横线 | 1052 | 628 |
| `┼` 十字 | 182 | 88 |
| `│` **竖线** | **0** | **94** |

也就是说：caption 说这是有限元网格，画面是**一摞横杠**——零件的轮廓是对的，**网格本身不在**。

改法：结构化网格在字符格里就是一格格的交叉，而交叉需要两个方向。原实现每行都画
`┼ ─ ─ ┼ ─ ─ ┼`，但行是相邻的，竖线没有地方落。**改成奇偶交替**：节点行画 `┼` 与 `─`，
其间的行只画 `│`（仅节点处）——上下各一个 `┼` 把它夹住，读起来就是穿过节点的连续竖边。
**格数与原来相同，而且总墨量还降了**（这正是 `density_probe` 一直提示 `pane_gauge_fem` 墨量偏高
的那张图）。

## 6 `_algo_greedy`：区间**没按结束时间排序**，且选出的两个区间**互相重叠**

`pane_exec_algo` 的第三栏是区间调度，下面印着 `按结束时间排序，能接上就接：贪心不回头`。实测：

```
ends in drawing order: [4, 12, 20, 5, 13, 21, 6, 14]   sorted by end time? False
the picked set: A[0,4]  C[14,20]  F[15,21]  H[9,14]
  C[14,20] vs F[15,21]  overlap=True
```

两处都错，而且是这一课的要害：

- **没有排序**——而"按结束时间排序"是贪心解决区间调度的**第一步**，也是它唯一精妙的地方；
- **选出的集合自己重叠**：会返回两个重叠区间的调度器不是调度器。

现在区间按结束时间排序、选中集合由**真正的贪心规则**算出（取最早结束的，然后取下一个开始得比它结束晚的），
caption 同时报出真实选中的个数与"两两不重叠"。图、字、算法三者这才一致。

## 7 `_dev/math_probe.py` 扩了四条检查

本批修的四条都属于同一类：**画面渲染完全正常、在框内、在动，而旁边的字在描述不存在的东西**——
这是任何"渲染类"探针都看不见的。所以它们全部进 `math_probe`：

| 检查 | 判据 |
|---|---|
| 六个倒数词 | 每个仪表把自己的词印在屏上（批次 37） |
| softmax | 能读出对角权重，是概率、且随训练上升（批次 37） |
| 归约 | 有"源图与类框同帧共存"的帧（批次 37） |
| **`cum 80%`** | **屏上有跨多行的 amber 曲线**（本批） |
| **`mesh`** | **屏上有竖线**（本批） |
| **`search 8`** | **屏上的节点 8 被点亮**（本批） |

### 7.1 写这三条检查时，我自己的探针错了两次

第一次：找"任何读作 8 的格子"，按扫描顺序取最后一个 → 抓到一个**文字行里的 8**
（报出 `marker='7'`，即左边是另一个数字）。树节点是 `标记 + 数字`，只能用**左邻是不是标记符**来定位。

第二次：要求标记是 `◎`（U+25CE）。但**环形只属于游走的搜索光点**，路径上的节点保持 `●` 并**变成 amber**
——所以"点亮"是**颜色**不是字形，我的判据会把画对的图判错。

两次都是"探针在判一个它还没搞清的对象"。**判据本身也要被验证**，这是本项目反复出现的一课
（`check_coverage` 的构造性绿灯、`glyph_probe` 的假阳性，都属同一类）。

## 9 本批未做的（数学审计剩余）

**仍是错误的**
- `c_c` 的越界红格是**死代码**（`over` 要求 `step >= n`，而 `i` 只到 `n-1`）。
- `c_db` 的 B+ 叶键 0..1507 **不含查询值 41827**。
- `c_os` 状态机转移错位（时间片到→blocked、I/O→exit）；%CPU 之和可达 35% 而声明 7.3%。
- DFD 图里出现两个「教师」。
- `dijkstra_cracks` **不是 Dijkstra**（`i==0` 无条件命中最短分支，基准还用了漂移中的 `y`）。
- `c_dl` 的"反向传播"只是沿 loss 曲线画 `\` 与 `/`，**不是计算图**。
- `g_burndown` 的 legend 写 `─` 实画 `·`；`g_assembly` 的 P5/P6 重合且「41 parts」对 6 个框。

**纯表达增益（不是错误）**
- 补真实坐标轴数值刻度、色阶 legend；把静态公式变成随歌词语义推进的计算过程；
- 让相关 pane 共享一个不变量（能量守恒／收敛曲线）；`2^53` 用真模型。

**一处等你拍板的设计冲突**（批次 37 §8 提出，仍未定）
- 02b §4.6 要求 `pane_love_class`（184.33–187.97）「全片唯一允许静止」，而 `clock_probe`
  要求每个 pane 都有运动。现在代码选了后者（把 `t` 传给 `hearts9` 触发心跳）。**保探针还是保设计？**
