## 2 `pane_motif_dijkstra`：从"裂纹"改成算法本身

用户："我要求的 dijkstra 是 dijkstra 算法，不是裂纹"。

**旧图是什么**：`Dijkstra 裂纹`——在一片 hash 代价场里，沿**最便宜的那条路**裂开一条缝。批次 43 把
里面的贪心换成了**真 Dijkstra**（`_crack_path`，代价 2071 vs 旧贪心 3342）。所以那张图**内容上确实用到了
Dijkstra**，但**算法本身在屏幕外**：看图的人只看到一条缝，看不到"取最小 d 的未定节点、松弛它的每条边"
这件事。这一条正是用户要的：**Dijkstra 是这张图的主题，不是它的实现细节**。

**新图**：把运行过程画出来。六个节点的带权图（3×2 点阵，所有边都是一段直线：`─` `│` `╲`），
右侧是标号表 `d[v]` / `π[v]`，底部一行写明当前这一步。

```
       4              5            d[v]  π[v]
   S──────────────A──────────────D   S  0   -   已定
   │╲             │              │   A  4   S   已定
   │  ╲           │              │   D  9   A   前沿
   │    ╲         │              │   B  2   S   已定
   │ 2    ╲       │ 1            │2  C  5   A   已定
   │       10 ╲   │              │   T --   -   未达
   │            ╲ │
   B──────────────C──────────────T        步 10/14  d[T] = --
       8              2
```

实现：

- **`_dijkstra_run()`**（`lru_cache`）真跑一遍 Dijkstra，返回**每个步骤的快照**——已定集合、`d` 数组、
  `π` 数组、这一步是什么。算法**就是**图：`d[T]` 最后是 7，路径 S-A-C-T。
  这不是"为了好看而画的流程"，快照是运行的产品。
- 共 **15 个快照 / 14 步**（6 次取出 + 8 次松弛），每步 **0.15 s** = 2.25 s，正好在这行的可见生命
  （142.00–144.16，2.16 s）内跑完，末尾留 0.7 s 空档后重来（`clock_probe` 仍要求它动）。
- 图里两个"松弛了但不改善"的步骤是**故意留的**：`B→C`（2+8=10，不改善）与 `T→D`（7+2=9 ≥ 7，不改善）
  ——算法里这两步最容易被人忽略，而底部那行把算式写出来（`松弛 B→C：10 → 2 + 8 = 10，不改善`）。
- **删掉被取代的代码**：`_crack_path` 与 `dijkstra_cracks` 整段删除。按批次 47 立下的规矩要分清
  "被取代"和"没用上"——这里是**被取代**（同一个 pane，用户点名换了画法），所以删，不留在文件里。
- **亮度**：第一版把未定边画在 `_ui(0.28)` 上，而 `_ui` 带着影片的全局衰减（142 s 时是 0.42），
  渲染出来是一张**空方框**。改成 `_ui(0.62)`，权重 `_ui(0.72)`；这是**看了渲染图**才发现的，
  和本批第 7 条是同一类问题。

## 3 `pixelsort`：两个缺陷叠在一起，第二个藏住了第一个

用户："GPU 像素排序在演出中没有视觉变化"。

批次 31 的审计量到"4.17 s 里只有 1 格在变"，于是补了趟数；**而那一格就是说明文字里的趟数本身**。
真正的代码是这样：

```python
seed = [hash(i, j) % 100 for i in range(w)]
seed.sort()          # ← 这一行
srt = seed[:]
for p in range(passes):   # 对**已经排好序**的列表做插入排序 = 空操作
```

① **`seed.sort()` 让整个排序成了空转**：插入排序作用在已排序的数组上不做任何改动，所以 `srt` 在
任何趟数下都是那张完整的渐变——**这一行就是"演出中没有视觉变化"**。审计数到的"1 格"是说明文字里的
趟数在变。

② **趟数被封顶在 6**：`min(1.0, ...) * 6`，而行宽是 95，而插入排序只动它已经走到的前缀。就算
①不存在，也只能排好前 6 格。

两处都修：`seed.sort()` 删掉；`passes` 改成**按行宽的比例**（`(t % 3.4) / 2.6 * w`，2.6 s 扫完、
0.8 s 停在完成态）。渲染三帧（62.6 / 63.6 / 64.6）确认：排序区从左向右扫过整行，未排序的一段是
原始 hash 的噪声。

**顺带修了性能**：`passes` 一放开，逐趟插入排序就是 O(w²)=9025 次比较 × 每帧 11 行，全片最差帧
从 t=193.69 挪到 **t=62.23（38.8 ms / 41.7 预算）**。改用闭式——插入排序走 k 趟后的状态**恰好**是
`sorted(seed[:k]) + seed[k:]`（第 p 趟把第 p 个元素插进前 p 个的有序前缀），对 4000 个随机行与原循环
逐元素比对 **0 处不同**——同一张画，O(w log w)。该帧回到 23 ms。

## 4 `fork` 炸弹下面那行字

用户："fork炸弹下面的文字中有乱码（？）"。

**不是乱码**：那行是 `:(){ :|:& };:  —— 十二代就是 4096`，也就是 fork 炸弹的一行本体，字符完全正确
（放大渲染逐字确认）。但用户的疑问是合理的：**十二格标点在任何别的屏幕上都等于解码失败**，
而这一屏其它地方全是带文字说明的图。所以改成：

```
本体  :(){ :|:& };:  — 自己调用自己，十二代翻到 4096
```

一行本体仍然在（那是这一屏在画的东西），但它现在被**指名**了，后面那句话也不必再让读者自己猜
`;:` 是什么意思。

另外 58.65–70.08 是篮球窗口（用户裁定"不动"），把飞机移出这一段也避免了两层同时盖住会话窗。

**歼-20 斜向飞**：`dy=-0.45`（原来是 `tilt=True, dy=0.30` 的浅轨）。`dy` 是**穿过画幅的斜率**，
从入画（y≈0.645）爬到出画（y≈0.195），是一次明确的爬升对角线；`tilt` 那个正弦小起伏去掉，
因为"斜向"要的是一条直的斜线。

**魔鬼鱼的白色噪点轨迹**（`fly(spray=1.0)`）：
- 采样点是**精灵的左边缘**在更早 `v` 时的位置（用 `_fly_at` 反算），所以轨迹**跟着游动的曲线弯**，
  而不是直线拖尾；
- 抖动点用 `(index)` 的确定性 hash，不用 `random()`——`clock_probe --selftest` 会把每一行画两遍
  比对，随机数会让它失败；
- 带宽是边缘左右 8 格、5 个采样（约 21 格长的尾巴）。**第一版按精灵自身的宽度取带（±30 格 × 15 个
  采样），渲染出来是一团雾**：噪声铺满半个屏幕，把底下的对话文字打碎。收窄后是一条尾巴。
- 成本：约 110 次 `put`，该帧实测 **19.4 ms**（预算 41.7）。

## 9 这一批的教训

**"量到了"和"量对了"是两件事。** 批次 31 的审计确实量到"4.17 s 里 1 格在变"——但那一格是**说明文字**。
一个探针数所有格子的差，就把"图在动"和"图上的字在动"当成了同一件事；而 `pixelsort` 的排序
**从写下那天起就没运行过**（`seed.sort()` 在排序之前）。同一个形状在本项目里出现过多次
（批次 43 的 `"" in "任何字符"`、批次 46 的九成顶格），共同点是：**探针问的问题比它以为的要宽**。

**用户说"看不出来"时，先怀疑"画了没有"，不要先怀疑"画得够不够大"。** 本批两条都验证了这一点：
Dijkstra 的边在 `_ui(0.28)` 下确实是空的，碎片在 `_ui(0.34)` 下确实是黑的——两条都不是审美问题，
是**在影片自己的全局衰减下，这两个等级不可能被看见**。
