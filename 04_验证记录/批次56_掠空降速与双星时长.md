## 1 运-20 降速：降速是一个"花钱"的问题

> 运20飞得太快了，导致其快飞出时残影较严重，适当降点速

原来的掠空是 **11.20–13.10（1.90 s）**，横穿 482 格（画幅宽 197 + 精灵宽 285）＝ **254 格/秒，24 fps
下每帧 10.6 格**。残影是这么来的：`tuikit.py:468` 的 `lighter(img, prev*0.42)`（本项目 `FX["trail"]`）
把上一帧留在 42% 亮度上，而飞机在收尾段*frac* 已经缩到 0.5–0.34（精灵 143→97 格宽），**每帧 10.6 格
的位移占它自身宽度的 7–11%**——上一帧那架飞机就明明白白留在后面。所以"降速"是对的，问题只是降到多少。

### 1.1 第一次尝试（3.4 s）被帧预算挡下来

按字面把窗口拉长到 **11.20–14.60（3.40 s，5.9 格/帧）**，然后 `frame_probe` 直接报红：

```
197x52 warm worst 51.3 ms at t=13.43  <-- OVER BUDGET        （预算 41.7）
```

`stage_probe` 在 13.43 的分项：`render_diff 19.63 + school_fx.draw 7.92 + draw_body 6.98 +
transition 6.07 + fx_apply 2.53 + fx_trail 2.22 + normalise 1.49 + footer 0.92`。

原因是**成本正比于飞机墨迹盖住多少画幅**，而一次整屏转场本身就值 24–34 ms（41.7 的 60–80%）。
把同一帧分别在"有飞机/无飞机"下量（`_b56time.py` 的手法，现在固化进 `_dev/frame_sweep.py`）：

| t | 有飞机 | 无飞机 | 飞机那一份 |
|---|---|---|---|
| 12.15（全屏覆盖） | 38.7 | 23.4 | **+15.3** |
| 12.70（page 转场中） | 45.4 | 23.9 | **+21.5** |
| 13.20（slide 转场首帧） | 56.7 | 33.8 | **+22.9** |

**结论：整屏精灵 × 整屏转场，这个组合在本片的预算里放不下。** 3.4 s 的窗口让掠空最宽的那段正好压在
12.47 的 page 与 13.20 的 slide 两个转场上。

### 1.2 第二个发现：旧窗口本来也超预算，只是机检从来没采到

为了挑窗口写了 `_dev/frame_sweep.py`（0–215 s，**步长 0.05 s，比 24 fps 的 0.0417 s 还密**，每个时刻取
4 遍最小值）。它给出的第一条结论不是关于新窗口的：

```
orig 11.20-13.10 (1.90 s)   最差 47.8 ms @ t=12.20   <-- OVER
```

**旧窗口的峰值帧一直在预算外**，而 `frame_probe` 报的是 40.4 ms——因为它采的是"网格 + 每个转场的中点"，
**掠空最宽的那一刻既不是网格点也不是转场中点**（半个批次里最大的精灵正好落在采样缝里）。批次 43 给
`frame_probe` 补过转场中点，这次轮到事件中点。

### 1.3 于是这一批里有渲染器

不能只把采样点补上然后把 47.8 记成"已知超预算"，所以把两处热点做了：

| 位置 | 改动 | 依据 |
|---|---|---|
| `tui_live.Screen.render_diff` | 一行一次 `write`（原来一行约 200 次小 `write`）；run 的起始列**直接用循环里已经在累加的 `col`**，不再调 `_text_w(run)`（那是一次生成器 + 每字符一次 `east_asian_width`） | 13.43 这一帧 19.63 ms 全在这一处；照片精灵每一格颜色都不同，一行就是 ~200 个单格 run |
| `school_fx.paste(fast=True)` | **循环范围先算一次**（285×90＝25 650 格 → 屏幕上最多 10 244 格），不再逐格判断出界；`bcol` 不再走生成器 | 每帧有 1.5 万格只是"走进来被丢掉" |

两处都是**等价改写**，不是取巧：`render_diff` 的转义流由 `_dev/ansi_probe.py` 解码回屏再与 buffer 对比
——**425 帧、0 处不一致**；`paste` 的裁剪由 `pane_probe`（0 problem / 78 pane × 6 尺寸）与
`trans_probe`（0 cell problem）兜住。改完 `tui_live._text_w` 就没有调用点了（它算的正是循环里 `col`
已经在累加的那个量），**按批次 55 的判例删掉**，不留"只为某一次需求存在的函数"。同一批帧上的前后对比
（同机器、同方法）：

| t | 改之前 | 改之后 |
|---|---|---|
| 12.15（峰值帧） | 34.3 ms | **25.7 ms** |
| 13.20（最差重叠帧） | 56.7 ms | **44.0 ms** |

两处各自值多少也单独量过（同一帧、把改动逐个打开/关掉）：**`paste` 的裁剪 4–7 ms**，其余是
`render_diff` 的。掠空自己的峰值帧（全屏覆盖、无转场）**47.8 → 38.1 ms**。

### 1.4 最终窗口：10.65–13.17（2.52 s，8.1 格/帧）

| 候选窗口 | 时长 | 速度 | 全曲该段最差帧 |
|---|---|---|---|
| 11.20–13.10（原） | 1.90 s | 10.6 格/帧 | 40.0 ms |
| 11.20–14.60（第一次尝试） | 3.40 s | 5.9 格/帧 | **45.3 ms ✗** |
| **10.65–13.17（采用）** | **2.52 s** | **8.1 格/帧** | **37.1 ms** |

为什么不是更长：`u` 的 0.28–0.72（墨迹盖住大部分画幅的那段）宽 0.44×时长，而 10.90 skew 转场与 12.47
page 转场之间**只有 1.11 s 无转场**，于是均匀窗口的上限就是 0.44d ≤ 1.11 → d ≤ 2.52 s。更长只能把最宽
那一段压到转场上，实测 42–51 ms（`11.20-14.20` → 偏 12.55；`10.90-13.20` → 偏 12.55）。

**代价与取舍**：2.52 s 是原速的 **76%**——"适当降点速"的字面兑现。如果还要更慢，唯一干净的办法是把整条
航线搬到 13.66–17.00 那段无转场的 3.34 s（何尊 pane，对应歌词 "但你会看到东西飞过去"），实测 3.4 s 窗口
在那里是 39.6–40.4 ms（能过，余量小），但那是把批次 49 用户裁定过"运20…可以保持不变"的航线挪走，所以
这一批没做，留给用户决定。

`SHOCKS` 跟着事件中心走：12.15 → **11.91**（窗口 11.61–12.21），仍在无转场段内。

## 2 双星旋进的时间

> 双星旋进的时间太短了，适当加点

`school_motifs.binary` 的时钟是**从自己那一行读的**（`_row_span("pane_motif_binary")`）：

```python
span = max(0.8, end - at)          # 行时长
vis  = max(0.5, span - 0.45)       # 前 0.45 s 是这一行自己的转场，旋进只算可见段
ph   = (t - at - 0.45) / vis       # 0→1，1 就是并合
```

所以**加长那一行就等于加长旋进**：1.43 s 的行 → `vis = 0.98 s`（`turns = ph + 1.6ph³` 约 2.6 圈，还没看清
就没了）；现在 **3.72 s → vis = 3.27 s（3.3 倍）**，并合闪光（`ph > 0.9`）也从 0.1 s 变成 0.33 s。
时间从 `pane_motif_pixelsort` 来：它原来 4.17 s，现在 1.88 s（`span_probe` 的 1.2 s 底线之上，且它画的
排序扫描是循环动画，长短都读得出来）。

**边界取的是歌词时间，不是整数**：第一版把 pixelsort 挪到 64.00——那是 "Then I can, then I can"（62.41）
中间，**是这首歌没有的边界**（这张表里 `at` 一律是 `input/lyrics.lrc` 的歌词时间）。改成 **64.29**，即
"Be your only satisfaction" 起唱处，pixelsort 那一行的 `lyric` 也改成这一句。后果是 "Then I can, then I
can" 现在落在双星这一行里（`06_` 的行内歌词随之变化），这是"给旋进加时间"必须付的那一笔。

**渲染确认**（`_dev/column_dump.py` 逐行读回右栏）：

| t | 读到什么 |
|---|---|
| 61.60 | 轨道画满整条框（第 16–22 行是一整圈 `·`），两颗星在轨道顶部 |
| 63.90 | 轨道缩到框中央一小圈，两颗星分列左右 |
| 64.20 | 中心并合闪光 `*·*·*·*·*·*`，字幕 `剩下  0.1 s：轨道越小，频率越高` |

此前 1.43 s 的行里，这三步要在 0.98 s 内全部演完（并合闪光只有 0.1 s）。

## 4 这一批的教训

**"降速"是帧预算问题，不是时间轴问题。** 把 1.9 s 改成 3.4 s 只花了一次编辑，代价却要到 `frame_probe`
才现形：本片最大的精灵（285×90）与整屏转场同时出现，两个各自的"贵"叠起来就是 51 ms。**先量窗口，再定
动画**，顺序反过来就要返工。

**探针的采样缝正好落在最大的东西上。** `frame_probe` 的网格 + 转场中点覆盖了转场，却漏掉了事件中点——
而"整屏精灵最大"这件事只发生在事件中点（旧窗口的 47.8 ms 就是这样躲过了每一个批次）。这一批两头都补：
**采样点**补上"每个整屏事件的中点"（99 → 114），**工具**补上 `_dev/frame_sweep.py`（任意区间逐帧扫描，
打印最差若干帧以及那时刻在播的事件/转场/pane）。两者顺序不能反：先有逐帧扫描证明"全曲 4301 帧 0 帧超
预算"，才敢动采样点——否则网格一改，红的是历史遗留还是新回归就分不清了。**下次动大图事件，先跑
`frame_sweep --lo … --hi …`。**
