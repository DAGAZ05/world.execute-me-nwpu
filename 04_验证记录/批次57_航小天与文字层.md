# 批次 57 · 航小天全身图被"文字层"压住：`behind` 是一个顺序，不是一个属性

> 学院部分航小天上下跳动的动画，有一小段航小天全身图没有位于最上图层，修改一下

---

## 1 先找到是谁压在它身上

跳动的全身图是 `stand` 事件（193.60–199.00，`FP.pulse` 驱动的跃动）。它画在**整屏层**里，之后的管线只有
三段：`school_fx.transition`（本变体自己的转场）→ 可能一次 `draw_lyrics` → `fx_apply`（reveal / trail /
shake）→ `normalise`。逐一包起来量"这一层往**精灵自己的矩形**（x127..190）里写了多少格"：

| 阶段 | 写入精灵矩形的格数 |
|---|---|
| `fx_reveal` 的 cut hold | **0** —— 实测 `_CUT[0]` 在 193.4–199.6 全程是 `None`（本变体的转场不走影片那套 reveal） |
| `school_fx.transition:zoom`（193.46–193.92） | **0** —— 它搬的是 pane 那一列（`_box = (1,1,97,47)`），精灵在右列 |
| `fx_apply`（trail / shake） | 每帧 2 格（幽灵/抖动） |
| **`draw_lyrics`（`covers_band` 的那次重画）** | **每帧 34–44 格** |

也就是说：**压住他的是"文字层"**。原因是布局——`BAND_BOX = [98, 35, 195, 47]`（stdout band 就是会话窗下半
那一段），而全身图站在右列 x127..190、脚到第 46 行，**他的身体横跨在这个盒子里面**。批次 26 给 `behind`
照片加的保险是从**层外**做的：

```python
# tui_live.draw，批次 26-56 的样子
_FX.draw(s, cols, rows, t)
_FX.transition(s, cols, rows, t)
if _FX.covers_band(t) and BAND_BOX[2] > BAND_BOX[0]:
    draw_lyrics(s, d, t, *BAND_BOX)          # ← 在整屏层之后重画文字
```

图书馆那张 `behind=True` 的照片活着 193.50–197.50，于是这四秒里每帧都把 band 重画一遍——**band 的框线
和文字因此画在了航小天的身上**。逐格取证（t=194.25，41 格，全部在第 35 行）：

```
cell (141,35) figure='▀' band='─'      ← 他身体的 `▀` 被 stdout 框的上边框 `─` 换掉
cell (142,35) figure='▀' band='─'
...                                     （t=194.50 是 34 格，同为第 35 行；格数随他在那一行的轮廓宽度变）
```

**损坏窗口**：193.625 → 197.50（图书馆结束），**102 帧 / 3.9 秒**，每帧 34–44 格。

## 2 修法：把"文字"放回它该在的层间位置

`behind` 的本意是"在这张照片**之上**写字"，那么正确的顺序是 **照片 → 文字 → 其它一切**；批次 26 的实现
把"文字"放到了"其它一切"之后，于是它同时压住了精灵。修法不是在重画时做裁剪（band 的文字是按整个盒子
排版的，裁一半就是把句子裁了），而是让**层自己拥有这个顺序**：

```python
def draw(s, cols, rows, t, words=None) -> int:
    # 两遍：先 behind 照片，再 words()（如果有 behind 事件画过），最后其余事件
```

`tui_live` 传给它的回调是新的 `_band_restore`（原 `covers_band` 的两行），`covers_band` 因此没有调用点，
**按批次 55 的判例删掉**，它 docstring 里那段"图书馆四秒没有歌词"的实测移进了 `_band_restore` 与事件表
的注释。顺序实测（t=194.50，包装 `_run` 与 `_band_restore` 记录调用次序）：

```
order at t=194.50: ['behind-photo', 'WORDS (band)', 'sprite/other']
```

**为什么先文字后转场也是安全的**：`transition` 搬的是 pane 那一列（x1..97），而 band 在 x98..195——实测
193.3–199.5 的 138 帧里，转场往 band 盒子里写了 **0 格**（`zoom` 那 11 帧同样 0）。渲染确认（t=194.50）：

```
35 |  ┌─ \ stdout · tokens ──────────────────────▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀────────────────────|
```

框线到他的身体就**停住**、在他另一边继续——**他在最上层**。

## 3 新探针 `_dev/layer_probe.py`：顺序是唯一查不了的东西

图片可以量墨、量颜色，**顺序不能**——它只能被测调用次序。新探针从 `school_fx.EVENTS` 自己算出"`behind`
事件与普通事件同时活着的窗口"（不手写时间），逐帧包装层与回调，断言：**每个 behind 事件在 words 之前、
每个普通事件在 words 之后**。

```
1 window(s) where a `behind` photograph and another event are both live:
   193.60 -  197.50  (3.90 s)
20 frame(s) checked; 0 with the wrong order
```

**它会在旧代码上失败**（否则就是装饰）：把 `school_fx.draw` 换成批次 56 那个"单遍、没有 words 回调"的
版本再跑一次 —— `4 frame(s) checked; 4 with the wrong order`，输出 `the words were drawn 0 time(s)`。
已加入 `check.cmd`（十四个探针 → **十五个**）。

## 5 这一批的教训

**"behind" 是句关于顺序的话，而顺序必须由拥有这两层的那个函数来保证。** 批次 26 把文字的补画写在了
调用方（`tui_live.draw`），那里只知道"这一层画完了"，不知道"层里还有精灵要画在他上面"；于是同一条规则
在一层上是"照片在文字下"，在另一层上变成"文字在精灵上"。**谁定义层次，谁排序**——这次把 `words` 回调
交给 `school_fx.draw`，规则就只有一份。

**"事后重画"这类补丁都要问一句：它画完之后，还有谁要画？** `_band_restore` 自己没问题（band 的内容就
是它该画的），出问题的是它在整条管线的位置。批次 26 的注释其实写过"它不是通用的'文字层永远在最上'机制"
——那句提醒是对的，只是没有人把它接到这条 4 秒的重叠上；现在探针替它盯着。
