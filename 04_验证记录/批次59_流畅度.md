# 批次 59 · 流畅度：把两个预算都量出来，然后各减一点

> 有什么办法增加画面流畅度吗？

回答这个问题之前先量——因为"流畅"在这个播放器里有**两个预算**，而此前只量过一个：

* **Python**：`_dev/frame_probe.py` 量它（对 24 fps 的 41.7 ms）；
* **终端**：`render_diff` 只写变化的格，可是**没人量过那是多少字节**。一张照片精灵横穿会改七千多格，
  若每格颜色都不同，就是每格一次光标移动 + 两条 24 位色转义。

新工具 **`_dev/paint_probe.py`** 逐帧（1/24 s，像播放一样彼此 diff）把两者一起打出来。结论是**终端那一侧
更大**：掠空段 Python 36.8 ms（27 fps），而终端每帧要重画 **212 KB / 14 379 条转义**（27 fps 下约 5.7 MB/s）。

## 1 改了什么（每一条都对着一个量出来的数）

| 改动 | 为什么安全 | 买到什么 |
|---|---|---|
| **`_wide_char` 记忆化** | 只缓存 `unicodedata` 的答案，行为不变 | 它每格调一次、每条 run 每个字符再调一次（满屏精灵一帧约一万次）。全曲 Python 均值 25.9 → **21.6 ms** |
| **diff 省掉重复的光标与色码**：run 的起点正好是光标所在列时不再发 `ESC[y;xH`；fg/bg 与上一条 run 相同时不再发色码 | `ansi_probe` 把转义流解码回屏再与 buffer 逐帧比对——**两变体各 425 帧 0 不一致** | 掠空段转义 14 379 → **9 642**（−33%）、字节 212 → **171 KB** |
| **单格 run 不再走列表+join** | 同上 | 照片上每格一色，这是绝大多数 run |
| **`paste(fast=True)` 折叠斜坡常数**：`k = drow[x]*(A + B*lv)` | 同一个算式重排 | 每格少一次除法一次乘法（本机在噪声内，未单独记功） |
| **图版路线不再逐格 `put` + 逐格调色**：新增 `_Kit.blit`，按"亮度"缓存已调好的颜色 | 这些网格由调用方夹在 body 矩形内，`put` 的裁剪是给**文字**用的 | 何尊那一版一帧约 5 200 格，掠空段 35 → **31 ms** |

全曲播放式复测（`paint_probe --full`）：**Python 均值 25.9 → 21.6 ms（38.6 → 46.2 fps）**，
终端均值 39.8 → **31.1 KB/帧**，最差 104.7 → 76.1 ms。窗口级：

| 窗口 | Python 均值 | 终端均值 | 转义数 |
|---|---|---|---|
| 14–16 s（运-20 掠空） | 36.8 → **31.4 ms**（27 → 32 fps） | 212 → **171 KB** | 14 379 → 9 642 |
| 60–64 s（双星） | 26.1 → 22.8 ms | 44 → 35 KB | 2 992 → 2 088 |
| 146–150 s（flood+执行） | 25.9 → 22.4 ms | 42 → 30 KB | 2 943 → 1 828 |
| 190–196 s（航小天+图书馆） | 27.5 → 23.7 ms | 55 → 43 KB | 3 721 → 2 481 |

## 2 一次量了但**没做**的改动

**把精灵的颜色降到 5–6 bit/通道**，让相邻格变成同一个颜色、从而让 diff 的 run 合并。理由是这么算的：
掠空段 7 225 格、9 642 条转义 ≈ 每格 1.3 条，若能合并就会掉一大截。实测（`SPRITE_BITS` 开关）：

| 位数 | 终端均值 | 颜色位移（对 8 bit 基准） |
|---|---|---|
| 8（今天） | 171.5 KB | — |
| 5 | 158.4 KB（−8%） | 最大 4/255、均值 1.5 |
| 4 | 146.8 KB（−14%） | 最大 8/255、均值 2.9 |

**只有 8–14% 的字节，却真的动了颜色**，所以放弃——原因写在记录里：精灵是**抖动过**的，抖动本身就保证
相邻格的色值不同，"让相邻格同色"这条路被它自己堵死了。`SPRITE_BITS = 8`（关）留在代码里，附这段结论。

## 3 循环的帧率上限：30 → 60（`--fps-cap`）

`tui_live.main` 是"画完再 sleep 到 1/30 s"，所以画面速率 = `min(30, 1000/帧 ms)`。改动前典型帧只要
22–24 ms（本可跑 42–45 fps），**那 30 是白白丢掉的三分之一**。影片自己的 24 fps 是*创作*速率，而所有动画
都是**歌曲时钟的连续函数**（飞机位置、轨道、斜坡、打字），所以多画的帧是真正的中间态、不是重复帧 ✓。

`FPS_CAP = 60.0`，并给了 `--fps-cap`（`--fps-cap 30` 就是旧行为）。代价是 CPU 与终端流量：帧率上去后
每秒发出的字节数同比上升，所以这一条排在 §1 之后做。

## 4 不用改代码的那一半（往往最大）

终端的重画吞吐是这套东西里唯一"代码之外"的变量：掠空段峰值 224 KB/帧，30 fps 下约 6–7 MB/s 的转义流。

* 用 GPU 终端（Windows Terminal 的 atlas 引擎 / WezTerm / Alacritty；conhost 最慢）；
* 关透明、亚克力、背景图、光标闪烁，滚动回看调小；
* **不要给播放器套管道**（`tee`、会话录制、harness 捕获）——同样这些字节穿过管道，就是几十 fps 和个位数
  的差别；
* 窗口别拉太大：197×52 是影片设计的尺寸，拉满到 300×90 就是 2.4 倍的格子；
* 播放时页脚每 0.5 s 打一次真实 fps，可以直接看这一条有没有生效。

## 6 这一批的教训

**"流畅"要问清楚是哪一半。** Python 的时间与终端的字节数是两个预算，量之前我给出的建议里有一半是猜的
（以为终端的 run 会因颜色量化而合并——实测只值 8–14%，因为精灵是抖动的）。**先写一个把两者一起打出来的
探针**（`paint_probe`），再谈优化顺序。

**上限也是一种浪费。** 30 fps 的 sleep 让"本可以 45 fps"的帧只出 30——而影片是 24 fps 创作的，多出来的帧
是连续函数上的真中间态。这个改动只有一行，收益却比前面所有微优化加起来更直接（典型帧 +40%）。
